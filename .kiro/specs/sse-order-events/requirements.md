# Requirements Document

## Introduction

This feature adds real-time Server-Sent Events (SSE) push delivery for order state changes to the WaffleFinance coordinator service. Currently, clients poll `GET /api/orders/history` on a timer to learn about state transitions. SSE eliminates polling lag so users see order transitions (announced → src_locked → dst_locked → secret_revealed → completed/refunded) within seconds of the on-chain event rather than waiting up to 15 seconds for the next poll tick.

The scope covers: the coordinator-side SSE endpoint and subscriber registry, wiring the existing `OrderService` transitions to broadcast events, a frontend SSE transport that integrates with the existing `OrderEventTransport` contract, a React hook (`useOrderStream`) exposing the stream to components, multi-instance deployment support via Redis Pub/Sub or sticky sessions, E2E push delivery tests, and API documentation.

## Glossary

- **SSE_Endpoint**: The HTTP endpoint `GET /api/orders/:id/events` that returns a `text/event-stream` response.
- **SSE_Broker**: The server-side component that manages subscriber connections and broadcasts order state events to all connected clients for a given order.
- **Subscriber_Registry**: The in-process data structure that maps an order `publicId` to the set of active SSE response streams watching it.
- **OrderService**: The existing coordinator service that drives order lifecycle transitions (announce, recordSrcLock, recordDstLock, recordSecret, markStatus).
- **SSE_Event**: A single server-sent event frame containing a `data` JSON payload, an optional `event` type field, and an `id` field for reconnect support.
- **Keep-Alive_Ping**: A comment line (`: ping`) emitted periodically on an idle SSE stream to prevent proxy and load-balancer idle-connection timeouts.
- **SSE_Transport**: A frontend `OrderEventTransport` implementation that opens an `EventSource` connection to the SSE_Endpoint and feeds observations into the existing `OrderObservationEmitter` contract.
- **useOrderStream**: A React hook that wraps `SSE_Transport` and the existing `createPollingTransport` into a merged transport via `mergeTransports`, providing a single unified stream with SSE as primary and polling as fallback.
- **Redis_PubSub**: An optional Redis Pub/Sub channel used to forward SSE events across multiple coordinator instances so that a client connected to instance A receives events generated by instance B.
- **OrderStatus**: The coordinator status union: `announced`, `src_locked`, `dst_locked`, `secret_revealed`, `completed`, `refunded`, `failed`, `expired`.
- **Event_Type**: The SSE `event:` field value identifying what happened: `OrderCreated`, `OrderClaimed`, `OrderRefunded`, `SecretRevealed`, `StatusChanged`, `ping`.

## Requirements

### Requirement 1: SSE Endpoint

**User Story:** As a client application, I want to subscribe to a persistent HTTP stream for a specific order, so that I receive state updates in real time without polling.

#### Acceptance Criteria

1. WHEN a client sends `GET /api/orders/:id/events` with an `Accept: text/event-stream` header, THE SSE_Endpoint SHALL respond with HTTP 200, `Content-Type: text/event-stream`, `Cache-Control: no-cache`, and `Connection: keep-alive`.
2. WHEN the `:id` path parameter does not correspond to an existing order, THE SSE_Endpoint SHALL respond with HTTP 404 immediately, regardless of the `Accept` header value, before upgrading to the stream.
3. WHEN the `:id` path parameter is present but malformed (fails the existing `orderIdSchema` validation), THE SSE_Endpoint SHALL respond with HTTP 400 before upgrading to the stream.
4. THE SSE_Endpoint SHALL set the `X-Accel-Buffering: no` response header to disable Nginx proxy buffering.
5. WHEN a client reconnects with a `Last-Event-ID` header containing a valid prior event ID, THE SSE_Endpoint SHALL replay any events for that order that were emitted after the last received ID, up to a configurable replay buffer size.
6. WHERE CORS is configured, THE SSE_Endpoint SHALL apply the same CORS origin policy as all other `/api` routes.

---

### Requirement 2: SSE Event Schema

**User Story:** As a client application, I want each event to carry a typed, versioned payload, so that I can parse and act on state changes without ambiguity.

#### Acceptance Criteria

1. THE SSE_Broker SHALL emit events in the SSE text format: an `id:` line, an `event:` line, a `data:` line containing a JSON object, and a blank line.
2. WHEN the order transitions to `src_locked`, THE SSE_Broker SHALL emit an event with `event: OrderCreated` and a `data` payload containing `{ orderId, status: "src_locked", srcChain, srcTxHash, blockNumber, timelock, timestamp }`.
3. WHEN the order transitions to `dst_locked` or `secret_revealed`, THE SSE_Broker SHALL emit an event with `event: OrderClaimed` and a `data` payload containing `{ orderId, status, dstChain, dstTxHash, blockNumber, timelock, resolver, timestamp }`.
4. WHEN the order transitions to `refunded`, THE SSE_Broker SHALL emit an event with `event: OrderRefunded` and a `data` payload containing `{ orderId, status: "refunded", txHash, timestamp }`.
5. WHEN `recordSecret` is called on an order, THE SSE_Broker SHALL emit an event with `event: SecretRevealed` and a `data` payload containing `{ orderId, preimage, revealedTx, timestamp }`.
6. WHEN the order transitions to any other status not covered by criteria 2–5 (e.g. `completed`, `failed`, `expired`, `announced`), THE SSE_Broker SHALL emit an event with `event: StatusChanged` and a `data` payload containing `{ orderId, status, previousStatus, timestamp }`.
7. THE SSE_Broker SHALL assign each emitted event a monotonically increasing integer `id` scoped to the order, to support `Last-Event-ID`-based reconnection.
8. THE SSE_Broker SHALL include a `timestamp` field in every event payload that is a Unix millisecond integer.

---

### Requirement 3: Keep-Alive Pings

**User Story:** As a client behind a load balancer or reverse proxy, I want the server to send periodic pings, so that idle connections are not silently dropped.

#### Acceptance Criteria

1. WHILE a client is connected to the SSE_Endpoint and no order event has been emitted in the preceding 30 seconds, THE SSE_Broker SHALL emit a keep-alive comment line (`: ping`) followed by a blank line.
2. THE SSE_Broker SHALL emit the first keep-alive ping within 30 seconds of the initial connection if no order event occurs in that window.
3. THE Keep-Alive_Ping SHALL NOT be interpreted as an SSE event by the client; it MUST be a comment line (starting with `:`) and SHALL NOT have an `event:` or `data:` field.

---

### Requirement 4: Subscriber Lifecycle and Disconnect Handling

**User Story:** As the coordinator service, I want to cleanly release resources when a client disconnects, so that memory and file descriptors are not leaked.

#### Acceptance Criteria

1. WHEN the client's TCP connection closes, THE Subscriber_Registry SHALL remove the corresponding subscriber entry within one event-loop tick.
2. WHEN an order reaches a terminal status (`completed`, `refunded`, `failed`), THE SSE_Broker SHALL emit the final event and then close the SSE stream with HTTP response end.
3. THE Subscriber_Registry SHALL impose a maximum of 1 000 concurrent SSE subscribers per coordinator process; IF the limit is reached, THE SSE_Endpoint SHALL respond with HTTP 503 to new connection attempts.
4. WHILE a subscriber is registered, THE SSE_Broker SHALL not hold a database connection open on behalf of that subscriber.
5. WHEN the coordinator process receives `SIGTERM`, THE SSE_Broker SHALL close all open SSE streams by sending a final `event: shutdown` frame before terminating.

---

### Requirement 5: OrderService Integration

**User Story:** As a developer, I want the existing `OrderService` transition methods to automatically broadcast SSE events, so that no new broadcast call is needed at each call site.

#### Acceptance Criteria

1. WHEN `OrderService.recordSrcLock` completes successfully, THE SSE_Broker SHALL broadcast an `OrderCreated` event to all subscribers watching that order's `publicId`.
2. WHEN `OrderService.recordDstLock` completes successfully, THE SSE_Broker SHALL broadcast an `OrderClaimed` event to all subscribers watching that order's `publicId`.
3. WHEN `OrderService.recordSecret` completes successfully, THE SSE_Broker SHALL broadcast a `SecretRevealed` event to all subscribers watching that order's `publicId`.
4. WHEN `OrderService.markStatus` completes successfully, THE SSE_Broker SHALL broadcast the appropriate typed event (OrderRefunded for `refunded`; StatusChanged for all other transitions) to all subscribers watching that order's `publicId`.
5. IF broadcasting to a subscriber fails, THEN THE SSE_Broker SHALL remove that subscriber from the Subscriber_Registry and SHALL NOT propagate the error to the `OrderService` call chain.
6. THE SSE_Broker integration with `OrderService` SHALL NOT introduce any additional database round trips per transition.

---

### Requirement 6: Replay Buffer

**User Story:** As a client that reconnects after a brief network interruption, I want to receive any events I missed, so that I do not display a stale order state.

#### Acceptance Criteria

1. THE SSE_Broker SHALL maintain an in-memory circular buffer of the last 50 events per order.
2. WHEN a client reconnects with a `Last-Event-ID` header, THE SSE_Broker SHALL replay all buffered events for that order with an `id` greater than the value in `Last-Event-ID`, in ascending `id` order.
3. IF the `Last-Event-ID` value is older than the oldest buffered event (gap too large), THE SSE_Broker SHALL emit a `event: replay-gap` frame indicating the client must re-fetch the current order state via `GET /api/orders/:id`.
4. THE SSE_Broker SHALL evict an order's replay buffer when the order reaches a terminal status and all subscribers for that order have disconnected.

---

### Requirement 7: Multi-Instance Deployment Support

**User Story:** As an operator running multiple coordinator instances behind a load balancer, I want order events to reach clients regardless of which instance they connected to, so that horizontal scaling does not break the push delivery guarantee.

#### Acceptance Criteria

1. WHERE `REDIS_URL` is set in the environment, THE SSE_Broker SHALL publish every order event to a Redis Pub/Sub channel named `order-events:{orderId}` immediately after broadcasting to local subscribers.
2. WHERE `REDIS_URL` is set, THE SSE_Broker SHALL subscribe to the wildcard Redis channel `order-events:*` and forward received messages to local subscribers for the corresponding `orderId`.
3. WHERE `REDIS_URL` is NOT set, THE SSE_Broker SHALL operate in single-instance mode using only the in-process Subscriber_Registry, with no external dependency.
4. IF the Redis connection is lost, THEN THE SSE_Broker SHALL continue operating in single-instance mode until the connection is restored; THE SSE_Broker SHALL attempt to log a warning but SHALL NOT treat a logging failure as a reason to stop operating.
5. THE Redis_PubSub message payload SHALL be identical to the SSE event `data` JSON, so consumers need no Redis-specific parsing logic.

---

### Requirement 8: Frontend SSE Transport

**User Story:** As a frontend developer, I want to use a drop-in SSE transport that satisfies the existing `OrderEventTransport` interface, so that SSE delivery requires no changes to consumers of the event stream.

#### Acceptance Criteria

1. THE SSE_Transport SHALL implement the `OrderEventTransport` interface defined in `frontend/src/lib/orderEventStream.ts`.
2. WHEN `SSE_Transport.start` is called, THE SSE_Transport SHALL open an `EventSource` connection to `{apiBaseUrl}/api/orders/{orderId}/events`.
3. WHEN an SSE event frame is received, THE SSE_Transport SHALL call `emitter.update` with an `OrderEventPayload` constructed via `createOrderEventPayload`, normalising the `event:` field to a canonical `OrderEventStatus` using the existing `COORDINATOR_STATUS_MAP` logic.
4. WHEN the `EventSource` fires an `error` event and the browser is online, THE SSE_Transport SHALL call `emitter.fail` with an `OrderEventError` of code `network`.
5. WHEN the `EventSource` fires an `error` event and `navigator.onLine` is false, THE SSE_Transport SHALL call `emitter.fail` with an `OrderEventError` of code `network` and set `retryable: true`.
6. WHEN the teardown function returned by `SSE_Transport.start` is called, THE SSE_Transport SHALL close the `EventSource` connection.
7. IF `EventSource` is not available in the runtime environment, THE SSE_Transport SHALL call `emitter.fail` with a `network` error on `start` so the `mergeTransports`-composed fallback polling transport can take over.

---

### Requirement 9: `useOrderStream` React Hook

**User Story:** As a frontend developer, I want a single hook that provides real-time order updates with automatic fallback to polling, so that the UI stays live even in environments where SSE is blocked.

#### Acceptance Criteria

1. THE `useOrderStream` hook SHALL accept an `orderId: string | null` parameter and return the same shape as `useOrderSubscription`.
2. WHEN `orderId` is non-null, THE `useOrderStream` hook SHALL compose an `SSE_Transport` and a `createPollingTransport` via `mergeTransports` and pass the merged transport to `subscribeToOrderEvents`.
3. WHEN `orderId` is null, THE `useOrderStream` hook SHALL return phase `'idle'` without opening any connection. If an internal `'connecting'` phase briefly occurs during initialization, THE hook SHALL resolve to `'idle'` before the first render is committed to the screen.
4. WHEN the SSE connection emits an event, THE `useOrderStream` hook SHALL update its returned `orders` map within one React render cycle.
5. WHEN the SSE connection fails permanently (exhausted), THE `useOrderStream` hook SHALL continue receiving updates via the polling fallback transport.
6. THE `useOrderStream` hook SHALL call `unsubscribe` on the active subscription when the component unmounts, ensuring no memory leak or dangling connection.
7. THE `useOrderStream` hook SHALL be referentially stable across re-renders when `orderId` does not change, preventing spurious effect re-runs in consuming components.

---

### Requirement 10: E2E Push Delivery Tests

**User Story:** As a developer, I want automated end-to-end tests that verify real-time SSE delivery through the full coordinator stack, so that regressions are caught before deployment.

#### Acceptance Criteria

1. THE E2E test suite SHALL include a test that announces an order, opens an `EventSource` (via Node.js or a test-compatible SSE client), triggers a `recordSrcLock` on the order, and asserts that the `OrderCreated` SSE event is received within 2 seconds.
2. THE E2E test suite SHALL include a test that verifies all five state transitions (`announced → src_locked → dst_locked → secret_revealed → completed`) produce the correct sequence of SSE events.
3. THE E2E test suite SHALL include a test that verifies a client reconnecting with `Last-Event-ID` receives only the events it missed and not earlier events.
4. THE E2E test suite SHALL include a test that verifies the keep-alive ping is emitted within 31 seconds when no event occurs.
5. THE E2E test suite SHALL include a test that verifies closing the client connection removes the subscriber from the Subscriber_Registry within 1 second.
6. WHEN any E2E test in this suite fails, THE test output SHALL include the sequence of SSE frames actually received to aid debugging.

---

### Requirement 11: Documentation

**User Story:** As a developer integrating with the coordinator, I want clear API documentation for the SSE endpoint and frontend hook, so that I can integrate correctly without reading source code.

#### Acceptance Criteria

1. THE SSE_Endpoint documentation SHALL describe the URL, required headers, response format, event types, field names and types, `Last-Event-ID` reconnection behaviour, and error responses (400, 404, 503).
2. THE `useOrderStream` hook documentation SHALL include a usage example, the full return type, fallback behaviour description, and a note on the `orderId` stability requirement.
3. THE documentation SHALL be placed in `coordinator/docs/SSE_API.md` for the backend and inline JSDoc in `frontend/src/hooks/useOrderStream.ts` for the hook.
